# Инструменты

Здесь два вида скриптов, и путать их не стоит.

## Постоянные

Запускаются регулярно — в сборке или при развёртывании.

| Скрипт | Что делает | Где вызывается |
|---|---|---|
| `check_duplicate_logic.py` | Следит, чтобы бизнес-логика не появлялась в `app/models` и не дублировалась с `app/services` | CI, задача backend |
| `audit_innerhtml.py` | Защёлка на неэкранированные подстановки в `innerHTML` | CI, задача frontend (`--check`) |
| `gen_allowlist.py` | Пересобирает реестр разрешённых обработчиков из разметки | CI сверяет, разработчик пересобирает после правки разметки |
| `verify_deployment.py` | Сравнивает заголовки и подключённые скрипты боевого сайта с тем, что в репозитории | Вручную после развёртывания |
| `set_down_revision.ps1` | Подставляет реальный `down_revision` в новую миграцию | Вручную при создании миграции |

## Одноразовые — в `migrations/`

Кодмоды под конкретные переходы. Каждый уже применён; повторный запуск ничего
не изменит, потому что все они проверяют текущее состояние перед правкой.

Хранятся не для повторного использования, а чтобы можно было понять, как
именно был выполнен переход. Когда через полгода возникнет вопрос «почему в
разметке вместо `onclick` стоит `data-onclick`», ответ будет виден в коде
скрипта, а не восстанавливаться по догадкам.

| Скрипт | Переход |
|---|---|
| `patch_limiter_await.py` | Синхронный клиент Redis → асинхронный: расстановка `await` |
| `fix_guards_async.py` | Он же, доводка: `async def` для функций-обёрток |
| `fix_async_defs.py` | Он же, общий случай: любая обычная `def` с `await` внутри |
| `patch_sensitive_handlers.py` | `data-nonce` для разрушительных обработчиков, безопасная подмена обложки |

## Инструменты приложения

Лежат отдельно, в `backend/tools/`: они работают с базой и импортируют
`app`, поэтому запускаются изнутри `backend`, а не из корня.

| Скрипт | Что делает |
|---|---|
| `create_e2e_user.py` | Заводит служебную учётную запись для браузерных проверок |
